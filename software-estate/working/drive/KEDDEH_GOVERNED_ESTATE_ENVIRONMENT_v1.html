Design rules

Conventions applied by this file itself.

Identity, class, evidence and boundary remain visible in dense engineering views. Essential state is not hidden behind hover interactions.
Color supplements state; it never carries state alone. Text labels and geometric markers remain present.
Interactive targets use a 44×44 px internal minimum even though external accessibility minima may permit smaller controls.
Monospace is reserved for machine identities, paths, hashes and protocol values. Prose remains system UI text for legibility.
Tables may be horizontally scrollable on small screens, but navigation and core state remain available without desktop-only assumptions.
Semantic HTML is preferred over custom drawn controls so browser accessibility, keyboard and platform behavior remain available.

Evidence levels

E0 — NAMEDIdentity is named, but no concrete carrier/evidence is established.
E1 — CARRIERConcrete carrier/custody is observed. This does not establish execution.
E2 — INTEGRITY + SURFACECarrier has integrity evidence and an implementation role/surface.
E3 — LOCAL EXECUTIONLocal execution/readback is observed. Must be backed by execution evidence, not inferred from source.
E4 — EXTERNAL MATERIALISATIONExternal/system boundary readback or authoritative receipt exists.
E5 — AUTHORITATIVE ACCEPTANCEExternal authority/network/service accepts the result where such acceptance is part of the system contract.

Claim discipline

The registry auto-derives only E0–E2 from static topology fields. E3–E5 are deliberately never inferred. They require runtime or external evidence. This prevents the particularly human engineering tradition of declaring victory because a file exists.
